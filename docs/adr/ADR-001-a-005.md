# Registro de decisiones de arquitectura (ADR)

Formato: Contexto → Decisión → Consecuencias. Estado: Propuesta hasta la Puerta 2.

---

## ADR-001 — Aplicación única modular

**Contexto.** El equipo es de dos personas y el plazo es de tres semanas.
**Decisión.** Una sola aplicación Spring Boot con paquetes por capa, no microservicios.
**Consecuencias.** Despliegue y pruebas simples y transacciones locales; si el sistema creciera, habría que separar módulos después.

---

## ADR-002 — Base de datos relacional

**Contexto.** Una producción debe descontar varios insumos y sumar el producto terminado como una sola operación, o no hacerse.
**Decisión.** Base de datos relacional (MySQL en `dev`) con Spring Data JPA y transacciones ACID.
**Consecuencias.** Integridad referencial y restricciones `CHECK` disponibles; el esquema se gestiona con `ddl-auto=update` (sin herramienta de migración, para no añadir dependencias).

## ADR-003 — Stock no negativo: validación, transacción y restricción

**Contexto.** RN-03 exige que el stock nunca sea negativo, incluso con operaciones simultáneas.
**Decisión.** Tres defensas, en este orden:
1. Validación previa del stock utilizable (excluye lotes vencidos) antes de operar.
2. Operación completa en una transacción (`@Transactional`) con bloqueo pesimista (`PESSIMISTIC_WRITE`) sobre los lotes consultados en orden FEFO.
3. Restricción `CHECK (cantidad_actual >= 0)` en `lote` y en el stock del producto como última barrera.

**Consecuencias.** Dos producciones simultáneas no pueden gastar el mismo lote; la restricción hace que un error de programación falle en vez de corromper datos. Cada caso de borde (AC-004.2, AC-004.3, AC-010.2) tiene prueba. Se implementa en el Sprint 2.

## ADR-004 — Sin capa service

**Contexto.** El documento del docente describe «controladores → servicios → repositorios». El 4 de noviembre el docente indicó, en la actividad de Spring, que al usar la librería JPA no debe haber capa `.service`: los controladores deben usar los repositorios directamente.
**Decisión.** No hay paquete ni clases `service`/`@Service`. Los controladores inyectan repositorios Spring Data. Las reglas de negocio viven en métodos de las entidades y en validaciones Bean Validation. Las operaciones de varios pasos se anotan `@Transactional` en el método del controlador. La auditoría se escribe con `EventoAuditoriaRepository` y con `@EventListener` de Spring Security.
**Consecuencias.**
- (+) Cumple la indicación del docente y reduce código.
- (−) Los controladores de producción y recepción (Sprint 2) serán más largos; se mitiga moviendo la lógica a métodos de dominio y a consultas del repositorio.
- (−) Se aparta de la Tabla 9 y del apartado «Tecnología y Arquitectura» del documento; se pide confirmación del PO en la Puerta 2 (D-07).

## ADR-005 — MySQL en todos los perfiles y despliegue en Render

**Contexto.** El equipo decidió que la base de datos debe ser MySQL y no H2. Render no ofrece MySQL.
**Decisión.** `dev`: MySQL local. `test`: MySQL local con esquema aparte `bakerstock_test` (`create-drop`). `cloud`: la aplicación corre en Render y se conecta a un MySQL en línea de otro proveedor mediante `DB_URL`, `DB_USER` y `DB_PASSWORD`. No se usa H2 ni otra base embebida.
**Consecuencias.** Las pruebas necesitan un MySQL local activo (el README explica cómo crear el esquema); el despliegue en línea espera a elegir el proveedor de MySQL (dato de conexión solo por variables de entorno). Si crear el esquema de pruebas resultara molesto, se puede evaluar Testcontainers, que es una dependencia nueva y exige permiso del PO. Se confirma en la Puerta 2 (D-06).
